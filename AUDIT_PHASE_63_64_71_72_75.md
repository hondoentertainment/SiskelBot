# Audit: Phase 63 / 64 / 71 / 72 / 75 Modules

Static analysis of 25 modules (`lib/*.js`, `tests/*.test.js`, `routes/*.js`)
shipped as WIP across Phase 63 (Code Generation), 64 (Research), 71 (Agent
Economics), 72 (Trust & Safety Pro), and 75 (Evaluation 2.0).

## Executive summary

- **25 / 25** modules have lib + test + route files present — none are missing.
- **Lib behavior:** 22 real, 2 partial (heuristic-only surrogates), 1 outright stub.
  - `lib/literature-search.js` is explicitly stubbed (deterministic mock, no HTTP, header comment states "stubs only").
  - `lib/test-gen.js` and `lib/refactor-agent.js` are real but shallow — they
    produce text artifacts but never touch the filesystem (refactor is regex
    find/replace only; test-gen emits a TODO-laden skeleton).
- **Tests:** 3 happy-only, 22 include at least some error-path / validation
  assertions. None are thorough in the end-to-end sense (no route-level
  supertest, no auth/scope coverage, no concurrent-write coverage).
- **Route middleware:** **0 / 25** use the canonical
  `logRequest → userAuth → requireScope(...)` chain from
  `routes/agent-sessions.js`. **All 25** use the non-standard
  `adminAuth, logRequest` pair (auth before logging, no scope enforcement).
  This is a systemic deviation, not a one-off.
- **Passing as-is:** 0 modules fully conform to project conventions (the
  middleware mismatch alone means every route file needs a touch-up).
- **Needing fixes:** 24.
- **Outright stubbed:** 1 (`literature-search`).

## Worst offenders

### 1. `lib/literature-search.js` — fully stubbed "integration"

The module advertises an "arXiv / PubMed / Semantic Scholar" unified interface
but returns deterministic fake results hashed from the query. A live-mode
toggle is documented in the header but never wired.

`/home/user/SiskelBot/lib/literature-search.js:6-9`
```
 * sources (arXiv, PubMed, Semantic Scholar). This module does NOT make live HTTP calls — it
 * returns deterministic mock results based on a hash of the query. A
 * live-mode toggle `LITERATURE_SEARCH_LIVE=1` is documented but not
 * wired up (stubs only).
```

`/home/user/SiskelBot/lib/literature-search.js:165-174` — `searchArxiv`
synthesizes results from a hash loop, no `fetch` call anywhere in the file:
```
export async function searchArxiv({ query = "", limit = DEFAULT_LIMIT } = {}) {
  const q = normQuery(query);
  const lim = clampLimit(limit);
  const out = [];
  for (let i = 0; i < lim; i += 1) {
    const id = deterministicIdForArxiv(q, i);
    out.push(mkResult({ query: q, source: "arxiv", index: i, id, urlPrefix: "https://arxiv.org/abs/" }));
  }
  return out;
}
```

Tests confirm the stub behavior rather than exercising a real backend
(`/home/user/SiskelBot/tests/literature-search.test.js:46-58` asserts
deterministic IDs). Action: either reimplement against the real APIs behind
the documented `LITERATURE_SEARCH_LIVE` flag, or delete the module and remove
its routes.

### 2. `lib/refactor-agent.js` — "apply" never writes to disk

`applyRefactor` claims to apply a refactor but the file header and code make
clear it is planning-only.

`/home/user/SiskelBot/lib/refactor-agent.js:1-9`
```
 * Phase 63.4: Refactoring agent (planning surface).
 * Computes hypothetical diffs for a transform without touching the filesystem.
 * ... `applyRefactor` with dryRun=false marks the plan applied but does not write
 *  to disk — callers write the files themselves using the plan's modified content.
```

The transform engine is a 20-line regex find/replace
(`/home/user/SiskelBot/lib/refactor-agent.js:36-56`) with only `rename` and
`replace` transform types. Anything resembling AST refactoring is absent. The
route exposes `POST /refactor/plans/:id/apply`
(`/home/user/SiskelBot/routes/refactor-agent.js:44`) implying it is applied,
but the function is a metadata-only status flip. Action: either rename the
endpoint to make the planning-only contract explicit, or extend the module
to actually persist changes (integrating with `workspace-fs-tools`).

The test
(`/home/user/SiskelBot/tests/test-gen.test.js:79-91`) only checks that the

### 4. Systemic middleware deviation across all 25 route modules

Canonical pattern from `routes/agent-sessions.js:19`:
```
apiRoute("post", "/agent/sessions", logRequest, userAuth, requireScope("write"), async (req, res) => {
```

Every Phase 63/64/71/72/75 route file instead uses:
```
apiRoute("post", "/<path>", adminAuth, logRequest, async (req, res) => {
```

Concrete examples (representative, all 25 follow this shape):

- `/home/user/SiskelBot/routes/repo-rag.js:15` — `adminAuth, logRequest`, no
  `requireScope`.
- `/home/user/SiskelBot/routes/credit-system.js:22` — financial mutation
  (`/credits/add`) gated only on admin auth; no per-scope check.
- `/home/user/SiskelBot/routes/invoicing.js:58` — `POST /invoices/:id/paid`
  uses `adminAuth, logRequest` (`apiRoute` order is reversed vs canonical;
  logging happens after auth rather than before).
- `/home/user/SiskelBot/routes/eval-in-prod.js:21`,
  `/home/user/SiskelBot/routes/synthetic-users.js:27`,
  `/home/user/SiskelBot/routes/safety-sla.js:16` — same pattern.

Impact: non-admin users never reach these endpoints (the feature is
effectively admin-only), `requireScope` write/read semantics are never
enforced, and the request log for auth failures is missing because
`logRequest` runs after `adminAuth` short-circuits. Action: migrate all 25
files to the canonical `logRequest, userAuth, requireScope(...)` chain or,
if admin-only is intentional, wrap with `logRequest, adminAuth` (swap the
order) and document the deviation.

### 5. `lib/migration-assistant.js` — in-memory cross-request index

`migrationIndex` is a module-level `Map` used to resolve
`migrationId → workspaceId` when callers omit `workspaceId`.

`/home/user/SiskelBot/lib/migration-assistant.js:33-34`
```
// Map migrationId → workspaceId.
const migrationIndex = new Map();
```

It is populated inside `startMigration`
(`/home/user/SiskelBot/lib/migration-assistant.js:109`) and read by
`loadMigration`
(`/home/user/SiskelBot/lib/migration-assistant.js:113-118`). On a server
restart, or in a multi-replica deployment where the follow-up request hits a
different process, the lookup fails silently and `loadMigration` returns
`{ migration: null, workspaceId: null }` — meaning `advanceMigration` and
`getMigrationStatus` quietly return `null` for a migration that exists on
disk. `refactor-agent.js` has the same bug with `planIndex`
(`/home/user/SiskelBot/lib/refactor-agent.js:30`). Action: persist the
index to disk (there's already a `workspacePath` pattern) or require
`workspaceId` on all callers and remove the Map.
